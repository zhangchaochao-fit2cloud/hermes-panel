# Orchestrator 多 Agent 编排 — 用户体验设计

> **核心命题**：怎么让用户不仅会用 Orchestrator，而且愿意常用、离不开？
> **设计原则**：用户只需要说"做什么"，不需要说"怎么做"。

---

## 一、用户为什么不用的 5 个原因（先解决阻力）

| 阻力 | 用户心里想的 | 解法 |
|------|------------|------|
| **不知道怎么触发** | "我该什么时候用 /orchestrate？直接问 AI 不行吗？" | 智能检测：系统判断任务复杂度，自动建议使用编排 |
| **等待时间太长** | "等 5 个 Agent 跑完不如我一个 Agent 聊 5 轮" | 并行执行 + 进度可视化 + 后台运行 |
| **结果不可控** | "万一架构师理解错了，后面全白跑了" | 计划预览 + 单步审批 + 随时干预 |
| **配置太复杂** | "我还得先定义角色、配工具、写 prompt？" | 12 个 Workspace 预配置，开箱即用，零配置启动 |
| **不知道省了多少事** | "跟直接聊好像差别不大？" | 结果对比卡：同样任务编排 vs 单 Agent 的时间/Token/质量对比 |

## 二、用户使用路径：四级递进

```
Level 0: 直接聊天 (现状)
  ┌─────────────────────────────────────┐
  │ 用户: "帮我加个登录功能"            │
  │ Agent: 自己做所有事，串行思考+执行  │
  │ 耗时: 长，容易丢上下文              │
  │ 质量: 还行，但单视角                │
  └─────────────────────────────────────┘
  用户感知: "AI 帮忙写代码"

  ↓ 系统自动检测任务复杂度，建议升级

Level 1: 一键编排 (零配置入口)
  ┌─────────────────────────────────────┐
  │ 用户: /orchestrate 加 OAuth 登录    │
  │ System:                             │
  │  📋 已自动分解为 5 步               │
  │  [开始] [编辑] [直接聊]             │
  │                                     │
  │ 用户: 点 [开始]                     │
  │ → 自动调度 5 Agent → 汇总结果       │
  │ 耗时: 短，并行执行                  │
  │ 质量: 高，多视角审查                │
  └─────────────────────────────────────┘
  用户感知: "AI 团队帮我做了一件大事"

  ↓ 用过几次后，想自定义流程

Level 2: 计划编辑 (预览 + 调整)
  ┌─────────────────────────────────────┐
  │ 用户: /orchestrate 重构 utils 模块  │
  │ System: 显示计划 DAG               │
  │                                     │
  │ 用户: 点「架构师」节点 → 补充:      │
  │  "注意保持向后兼容，v1 API 不能动"  │
  │                                     │
  │ 用户: 移除「移动端」节点 (不相关)   │
  │ 用户: 点 [开始]                     │
  └─────────────────────────────────────┘
  用户感知: "我指挥 AI 团队，它们执行"

  ↓ 经常做同类任务，想固化流程

Level 3: 保存为模板 (复用)
  ┌─────────────────────────────────────┐
  │ 用户: 完成一次重构 → 点 [保存模板]  │
  │ 命名为 "代码重构标准流程"           │
  │                                     │
  │ 下次: /wf 代码重构 → 直接执行       │
  │ 可分享给团队                        │
  └─────────────────────────────────────┘
  用户感知: "我有自己的 AI 工作流库"

  ↓ 高级用户想精细控制

Level 4: Workflow Editor (可视化编辑)
  ┌─────────────────────────────────────┐
  │ vue-flow 拖拽画布                   │
  │ 从节点面板拖拽 Agent/工具/条件分支  │
  │ 连线定义依赖关系                    │
  │ 设置并行/串行/超时/回退策略         │
  └─────────────────────────────────────┘
  用户感知: "我在设计 AI 工作流"
```

**关键设计决策**：每级之间是自然过渡，不是功能堆砌。Level 0→1 是系统主动引导，1→2 是用户自然需求，2→3 是习惯养成，3→4 是高级能力。

## 三、Level 1 详细设计：一键编排

这是最关键的一级——如果 Level 1 体验不好，用户永远不会到 Level 2-4。

### 3.1 触发方式：三种入口

```
入口 1: 智能建议 (被动触发)
  Composer 输入框中，用户输入超过一定复杂度时，
  输入框下方出现建议条：

  ┌─ Composer ────────────────────────────────────────────┐

入口 2: 命令触发 (主动触发)
  /orchestrate <任务描述>
  /orch <任务描述>  (短别名)
```

## 四、让用户「常用」的 5 个机制

### 4.1 智能升级建议（Trigger）

系统不该等用户想起 `/orchestrate`，而应该主动提示。

```
触发条件：
  1. 消息 > 150 字 AND 涉及多个技术领域
  2. 提到多个步骤 ("先...然后...最后...")
  3. 同一任务在单 Agent 下超过 5 轮还没完成
  4. 用户手动 @召唤了 2 个以上角色
  5. 任务类型匹配已有工作流模板

提示方式（递减侵扰）：
  第 1 次: Composer 下方建议条 (如上)
  第 2 次: 建议条 + "上次你类似的登录任务用了编排，快了 2x"
  第 3 次及以后: 不提示 → 如果用户仍未使用，说明他真的不需要
```

### 4.2 可见的对比价值（Reward）

每次编排完成后，显示对比卡。用户需要**看到**编排的价值：

```
┌─ 📊 编排 vs 单 Agent ───────────────────────────────────┐
│                                                          │
│               直接聊        编排模式         节省         │
│  ───────────────────────────────────────────────────    │
│  完成时间      8m30s        3m12s           ▼ 62%       │
│  Token 用量    68K           42K             ▼ 38%       │
│  成本          $0.41         $0.23           ▼ 44%       │
│  代码文件      3             5               ▲ +2       │
│  安全审查      ❌ 无         ✅ 已审查                   │
│  测试覆盖      ❌ 无         ✅ 12 个用例                │
│                                                          │
│  ───────────────────────────────────────────────────    │
│  累计节省 (本月): 24 分钟 · $2.13 · 多了 8 个测试        │
└──────────────────────────────────────────────────────────┘
```

### 4.3 渐进式信任建立（Trust）

```
第 1 次使用:
  ✅ 计划可编辑 → 用户有控制感
  ✅ 每步结果可展开查看 → 用户能验证质量
  ✅ 任何时刻可暂停/停止 → 用户有刹车

第 3 次使用:
  ✅ 系统记住用户偏好 ("你上次跳过了前端步骤")
  ✅ 计划准确率显示: "最近 5 次计划 4 次无需修改"

第 10 次使用:
  ✅ 可开启"自动执行"模式 → 跳过计划预览，直接跑
  ✅ 失败自动回退 → "QA 步骤失败，自动换了测试策略重试"
```

### 4.4 模板积累（Investment）

用户创建的工作流模板是**沉没成本**，越积累越离不开：

```
我的模板库:
  📋 代码重构标准流程       使用 23 次 · 上次 2 天前
  📋 新功能全栈开发         使用 15 次 · 上次 1 周前
  📋 PR Review 深度审查     使用 8 次 · 上次 3 天前
  📋 数据库 Migration        使用 5 次 · 上次 1 天前

社区热门:
  🔥 React 组件迁移 (v18→v19) · 安装 1.2K
  🔥 API 文档自动生成 · 安装 890
```

### 4.5 失败优雅降级（Safety Net）

编排失败时不等于任务失败——应该让用户有退路：

```
┌─ ⚠️ 编排部分完成 ──────────────────────────────────────┐
│                                                        │
│  ✅ 架构设计完成                                        │
│  ✅ 后端 API 实现完成                                   │
│  ❌ 前端 UI 超时 (模型响应慢)                           │
│                                                        │
│  已完成的部分可以使用                                    │
│                                                        │
│  [重试失败步骤]  [换模型重试]  [转直接聊继续]           │
└────────────────────────────────────────────────────────┘
```

## 五、让用户「用好」的 4 个细节

### 5.1 正确的问题粒度

```
❌ 太粗 (编排无意义):     "帮我改个变量名"
❌ 太细 (Agent 空转):     "帮我设计数据库，然后用这个设计实现 API，然后..."
✅ 刚好:                  "帮我实现用户邀请功能"
✅ 刚好:                  "重构 utils 模块，拆成独立子模块"
✅ 刚好:                  "Review 这个 PR 的安全性"

判断规则:
  - 单 Agent 预计 > 3 轮对话 → 适合编排
  - 涉及 2+ 技术领域 → 适合编排
  - 用户不确定从哪开始 → 适合编排 (让架构师先分析)
```

### 5.2 Plan Preview 应该是"建议"不是"决定"

```
系统自动生成计划后，用户可以做：
  ✅ 点某个步骤 → 补充说明 ("注意保持向后兼容")
  ✅ 点某个步骤 → 切换角色 ("后端不用 DeepSeek，用 Sonnet")
  ✅ 拖拽步骤 → 改变顺序或并行关系
  ✅ 移除/添加步骤
  ✅ 点 [直接聊] → 完全不用编排了，把计划当分析参考

计划是起点，不是终点。
```

### 5.3 上下文传递要透明

```
每个 Agent 收到的 prompt 应该让用户知道（可折叠查看）：

┌─ 🏛️ 架构师 收到的上下文 ────── [展开] ─────────────────┐
│                                                          │
│  ## 任务                                                   │
│  实现用户邀请功能                                         │
│                                                          │
│  ## 项目背景                                               │
│  Hermes Panel · pnpm monorepo · Vue3+Koa+Tauri            │
│  已有认证系统 (auth.ts, token.ts)                         │
│                                                          │
│  ## 你的职责                                              │
│  你是架构师角色。请设计邀请码的数据模型、校验规则、       │
│  API 结构。输出 ADR 格式的架构决策记录。                  │
│                                                          │
│  ## 可用工具                                              │
│  read_file, write_file, search_code                      │
│                                                          │
│  ## 约束                                                  │

│  - 邀请码 24h 过期, 一次性使用                            │

```

### 5.4 可以跟任何 Agent 直接对话

编排过程中，用户可以随时"插话"：

```
编排正在运行中:
  🔵 Step 3 后端正在实现 API

用户在 Step 3 卡片上点 [💬 对话]:
  → 打开与后端 Agent 的直接对话
  → 用户: "记得加 rate limiting"
  → 后端: "收到，已在 middleware 中增加 rate limit 配置"
  → 回到编排流程，后端继续

编排不应该是黑盒。
```

## 六、技术实现要点

### 6.1 Orchestrator 引擎核心流程

```typescript
// orchestrator.ts 伪代码
async function orchestrate(input: string, workspace: Workspace) {
  // 1. 意图分析 (快速廉价模型, < 1s)
  const intent = await analyzeIntent(input)    // → { type: 'feature', domains: ['backend','frontend','security'] }

  // 2. 任务分解 (廉价模型, 1-2s)
  const tasks = await decompose(input, intent, workspace.roles)

  // 3. 角色匹配 (规则引擎, 无需模型)
  const plan = matchRoles(tasks, workspace.roles)  // → DAG with assigned agents

  // 4. 返回计划给用户预览
  return plan
}

async function execute(plan: Plan, onProgress: (ev) => void) {
  // 5. 按 DAG 依赖关系调度
  const dag = buildDAG(plan.nodes)
  const parallelGroups = dag.topologicalGroups()

  for (const group of parallelGroups) {
    // 同组并行执行
    await Promise.all(group.map(node =>
      executeNode(node, onProgress)
    ))
  }

  // 6. 汇总
  const summary = await aggregate(plan.nodes.map(n => n.result))
  return summary
}
```

### 6.2 关键决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 意图分析模型 | 当前 Workspace 中最便宜的模型 | 避免编排本身成本过高 |
| 计划生成时间 | 目标 < 3 秒 | 超过 3 秒用户会不耐烦 |
| 并行策略 | 无依赖的步骤自动并行 | 最大化速度优势 |
| 失败策略 | 单步失败不阻塞兄弟节点 (fail-fast=false) | 部分结果 > 没有结果 |
| 状态存储 | panel.db workflow_runs 表 | 跨重启可恢复 |
